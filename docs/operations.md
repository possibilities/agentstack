# Operations

## Build and verification

`scripts/install.sh --install` installs the pinned codexnk release, builds AgentStack, and links its command. `pnpm test` builds packages and runs their compiled tests. `pnpm build` prepares the owner-served UI; do not rebuild its `.next` under a live owner without coordinating a restart.

## State and processes

State defaults to `~/.local/state/agentstack`; set `AGENTSTACK_STATE_DIR` for disposable checks. The owner runs `api`, `auth`, `bots`, `roles`, and `workers` socket children, a shared WebSocket child, Inspector, and UI canvas. It serves the `owner` Package API, discovery reference, and MCP HTTP in-process. Each Package API has `<state>/sockets/<name>.sock`. Bots launch codexnk on fresh opaque `<state>/app/<nonce>.sock` URLs. Read the reported `url` rather than deriving a socket path.

The Bots Package API owns every managed Codex process. `bot_start` with `{}` reserves the next `bot-N` and creates `<state>/bots/bot-N` with mode `0700`. A caller can supply `id`, an existing `cwd`, and Codex `args` for the previous `server_start` control. Existing bots reuse their recorded directory and arguments. A different directory cannot be substituted for an existing ID. `args: []` clears saved arguments while stopped; a running bot rejects changes. The raw array lives in `<state>/secrets.sqlite` and is absent from `bot_list`. `bot_remove` deletes a bot's private runtime, history, log, and default workspace, but leaves an external working directory intact. Previously recorded named Codex Servers are listed as Bots with their IDs and directories preserved. The existing SQLite `servers` table and `secrets.server_args` table remain the on-disk migration format.

Every Bot launch supplies `sandbox_mode="danger-full-access"` and `approval_policy="never"` as baseline codexnk CLI config overrides before saved caller `args`. Codex's later `-c` arguments can narrow either setting. An explicit `args: []` removes caller overrides and restores those defaults. These settings govern the app-server's future turns; managed or system policy may still constrain them. The baseline is not persisted as caller arguments or returned by `bot_list`.

An account is an immutable UUID managed by `auth`. The active account binds to a new bot; without one, a bot can launch unbound but cannot take a turn. `bot_assign` records a different account on an existing bot without restarting it. The view's `account` is the assignment and `runningAccount` is the live process identity. Stop and start to apply it. Removing an account fences new launches, removes bots assigned to or last launched with it (including a bot pending reassignment), then removes credentials. A failed removal remains retryable under the same ID. Credentials and runtime copies are private; a strictly later valid refresh can replace the saved generation. Ambiguous or stale copies are retained for inspection rather than replacing newer credentials.

Grok and Devin Worker accounts use `worker_account_prepare` with `{ "provider": "grok" }` or `{ "provider": "devin" }`; for a Codex worker pass `{ "provider": "codex", "id": "<existing Codex account UUID>" }`. This reserves a private native profile and returns its exact sign-in command. Run that command in a terminal, then call `worker_account_confirm` with its ID. Passing an existing Grok or Devin ID to prepare begins re-sign-in for that binding. `worker_account_list` reports all worker bindings; Codex entries without an OpenCode login report `ready: false`. `worker_account_set_enabled` controls Grok and Devin admission; `worker_account_remove` deletes only those accounts. `account_remove` remains the Codex removal path. Worker account mutations from a Bot-bound MCP call are refused.

The `workers` Package API's `worker_runtime_list` reports each owned ACP process. `worker_catalog({accountId})` reports account-bound ACP model IDs and dependent effort choices, a source/version, observation time, and stale/error state. `refresh: true` bypasses the thirty-minute cache, with concurrent refreshes coalesced. Devin's native model IDs are reported separately because the ACP selector may use different IDs. Catalog discovery creates no inference turn. This foundation has no Bot worker-session or turn operations yet. Use `AGENTSTACK_NATIVE_ACP_PROBE=1 node --test packages/workers/dist/test/native-probe.test.js` for a no-turn probe of installed harnesses after building the package; it uses the operator's existing native logins and a disposable working directory, not an AgentStack account binding.

A fresh bot starts with `mainThreadId: null`. Connect a UI to its `url` (for example, `codex --remote unix://…`) and send a first durable turn. The first persistent root thread with a materialized turn becomes the main thread. Later launches resume that ID and do not substitute another thread after a failed resume. Additional top-level Codex threads are outside AgentStack's bot view. Bot-scoped `threads_changed` notices invalidate state; they do not prove that the sanctioned lineage changed. An optional event scope allows a client to observe one Bot; unscoped subscriptions receive global `voice_changed` and bot notices.

The `bots` Package API also owns one ephemeral voice call across all bots. `voice_dial` takes a `botId`, client-generated `sessionId`, and gathered WebRTC SDP offer; it requires a verified running bot with an account and main thread. `voice_status`, `voice_hangup`, and `voice_changed` report and control the call without creating a new thread or transporting media through AgentStack. The canvas uses these operations for its call control.

On each launch, the bot snapshots the single role and currently configured owner MCP URLs into a private directory passed via codexnk's required `--capabilities` flag, with `SYSTEM_APPEND.md`, `config.toml`, and enabled role-owned skills under `skills/`. Additional enabled HTTP and stdio role MCP servers join the internal connections only in that private `config.toml`. `roleRevision` is the last launched revision; edits affect the next launch. The role's `roles.sqlite` database imports the previous `capabilities.sqlite` when first opened; legacy per-launch paths remain recognized for cleanup. The private identity directory is created even for an unbound bot, so the launch never falls back to ambient Codex credentials. The executable is always `~/.local/libexec/codexnk/codex`.

The Role can also hold explicit trusted project roots. A Bot launched within an enabled root receives only that matching `[projects]` trust entry in its private `config.toml`; unrelated and disabled roots are omitted. The pinned codexnk release uses it to load project `.codex/config.toml`, including project MCP servers, while excluding home-installed skills and personal marketplaces. Already running Bots retain their prior launch behavior; loading the new runtime requires a separately authorized Bot stop/start or owner restart.

Each internal MCP URL in a bot's private launch config carries a bot ID, a launch-instance digest, and a proof signed with `<state>/mcp-bot-identity.key` (mode `0600`). The owner validates that proof and checks the current `bot_list` state before forwarding a tool call. A stopped or restarted bot's old URL cannot call tools. Codex tool calls include `threadId` (and sometimes `sessionId`) in MCP `_meta`; a bot-bound tool call without a thread ID is refused. The owner passes `{ transport: "mcp", botId, instance, threadId, sessionId }` to the Package API operation as an optional third argument, separate from its public input schema. This is correlation metadata, not proof that the thread belongs to the Bot's sanctioned root; a turn-targeting workflow must verify lineage. The owner's published MCP URLs remain ordinary local-user endpoints for humans and other local clients.

### Agent-facing event subscriptions

The owner-managed MCP transport adds four tools to every event-bearing Package API: `events_catalog`, `events_subscribe`, `events_status`, and `events_unsubscribe`. `events_catalog` lists topic descriptions, the optional or required scope, and read-only operations with their input schemas. An agent calls `events_subscribe` from its bot-bound MCP connection with `{ "topic": "…", "readOperation": "…", "readArguments": {}, "scope": "…" }`. The read operation must belong to that Package API and advertise `readOnlyHint`. For a scoped Bots event, omitted `scope` defaults to the caller's bot ID. The tool subscribes first, then returns a current value and a durable subscription ID. Repeating the same request on that thread returns its existing subscription. A bot cannot subscribe its own thread to `threads_changed`, because delivery itself would create another thread notice.

Subsequent notices cause a fresh read and, if its value changed, a `turn/start` containing the package, topic, scope, read operation, and current value on the subscribing thread. Bursts coalesce to the latest state. Values over 16,000 characters yield a bounded turn pointing to the read operation for the full value. The owner serializes deliveries for a thread, waits for it to become idle, and checks the Bot launch and main-thread lineage again before starting the turn. It waits for that turn to complete before delivering another. A failed or ambiguous turn attempt is recorded in `events_status`; it is never blind-retried. Subscriptions live in private `<state>/event-subscriptions.sqlite` and reconnect after socket or owner restart, taking a fresh snapshot and rebinding to the current verified Bot launch. `events_unsubscribe` removes one exact ID for the same Bot thread. An unloaded thread remains in error/retry state until it returns or is unsubscribed; a deleted Bot's subscriptions are pruned on rebind. No other thread is substituted. Notices are invalidations, not a replayable event history.

On startup, the Bots Package API verifies recorded process ownership, reaps children from a previous owner, and relaunches recorded bots, including stopped ones. An unverified PID/endpoint pair remains fenced with `recoveryIssue`; it is not killed merely because the record says running. A verified stop clears the issue. An existing Package API socket is never unlinked to claim a second instance. If `<state>/sockets/bots.sock` is left by a crash, inspect its listener and owner before removing only that verified stale path. App-server sockets are cleaned only after their known child stops.

The owner refuses a second `serve` against a running instance and checks fixed ports before claiming sockets. On shutdown it closes public ingress, drains active calls while dependencies remain, then stops `auth`, `workers`, `bots`, `roles`, and `api` in order. The Workers child stops its ACP processes and the Bots child stops its app-server processes. The owner does not restart failed children automatically. The owner-served reference and `/x` canvas reflect the live Package API catalog and have markdown twins at `/docs/index.md` and `/x.md`; the index at `/` has `/index.md`.
