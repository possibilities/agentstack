# Operations

## Build and verification

`scripts/install.sh --install` installs the pinned codexnk release, builds Stack, and links its command. `pnpm test` builds packages and runs their compiled tests. `pnpm build` prepares the server-served UI; do not rebuild its `.next` under a live server without coordinating a restart.

## State and processes

The UI entry `/` serves Fleet. The System space (`/system`) contains the running MCP Inspector link, full MCP URLs, server child processes, and host/resource sampling windows. Fleet cards expose Bot workspaces and endpoints; clicking a card's name opens its complete record in the inspector. Accounts contains Usage and Model catalogs; Fleet contains Bot lifecycle controls, tools and chat windows. Space navigation switches isolated benches, restoring each camera and retaining inspection.

State defaults to `~/.local/state/stack`; set `STACK_STATE_DIR` for disposable checks. The server runs `access`, `api`, `auth`, `bots`, `brain`, `browse`, `content`, `infer`, `notify`, `proc`, `roles`, `scrape`, `signal`, `usage`, and `worker` socket children, a shared WebSocket child, Inspector, and UI canvas. It serves the `serve` Package API and MCP HTTP in-process. UI hosts the integrated Package API reference. Each Package API has `<state>/sockets/<name>.sock`. Bots launch codexnk on fresh opaque `<state>/app/<nonce>.sock` URLs. Read the reported `url` rather than deriving a socket path.

The Bots Package API owns every managed Codex process. `bot_start` with `{ "account": "<enabled Codex account UUID>" }` reserves the next `bot-N` and creates `<state>/bots/bot-N` with mode `0700`. The account is required even when starting an existing Bot and must match its saved assignment. A caller can supply `id`, an existing `cwd`, and Codex `args` for the previous `server_start` control. Existing bots reuse their recorded directory and arguments. A different directory cannot be substituted for an existing ID. `args: []` clears saved arguments while stopped; a running bot rejects changes. The raw array lives in `<state>/secrets.sqlite` and is absent from `bot_list`. `bot_remove` deletes a bot's private runtime, history, log, and default workspace, but leaves an external working directory intact. Previously recorded named Codex Servers are listed as Bots with their IDs and directories preserved. The existing SQLite `servers` table and `secrets.server_args` table remain the on-disk migration format.

Every Bot launch supplies `sandbox_mode="danger-full-access"` and `approval_policy="never"` as baseline codexnk CLI config overrides before saved caller `args`. Codex's later `-c` arguments can narrow either setting. An explicit `args: []` removes caller overrides and restores those defaults. These settings govern the app-server's future turns; managed or system policy may still constrain them. The baseline is not persisted as caller arguments or returned by `bot_list`.

Bot and Worker accounts have immutable UUIDs managed by `auth`. Every Codex Bot account has a paired Codex Worker with a separate native sign-in for the same ChatGPT login; both inventories report the pair in `linkedAccounts`. `account_list` shows `enabled` and `removing`; `account_set_enabled({id, enabled})` fences new Bot launches without stopping running Bots. `bot_start` requires an explicit enabled Bot account ID; `bot_assign` records a different one without restarting it. The view's `account` is the assignment and `runningAccount` is the live process identity. Stop and start to apply it. `account_remove` deletes bound Bots and its paired Codex Worker, drains their runtimes and removes their credentials. Other Worker accounts are untouched. A failed removal remains retryable under the same ID. Credentials and runtime copies are private; a strictly later valid refresh can replace the saved generation. Ambiguous or stale copies are retained for inspection rather than replacing newer credentials. Usage is observational and never chooses an account.

Grok, Devin and Claude Worker accounts can be created with `worker_account_login_start` and the matching `provider`. For a Codex Worker, pass the ID of the Worker created with its paired Bot account. The service runs native sign-in and returns an attempt state with a link (and a one-time code for Codex/Grok) for the human to open manually; completion confirms the Worker automatically. For a paste-back flow, `needsCode` enables `worker_account_login_submit`. Poll `worker_account_login_status` or subscribe to `worker_login_changed`; `worker_account_login_cancel` abandons an attempt. Passing an existing Worker ID begins re-sign-in for that Worker only. As a terminal fallback, `worker_account_prepare` returns the exact sign-in command and `worker_account_confirm` marks the account ready. `worker_account_list` reports `ready` and `enabled` independently; `worker_account_set_enabled` fences Worker turns and drains its runtime. `worker_account_remove` removes directly managed Workers; a paired Codex Worker is removed with its Bot account. A Claude Worker uses a separate native sign-in, not an imported AgentUsage or ambient Claude login. Account mutations from a Bot-bound MCP call are refused.

API-run sign-in is copy/paste-only. On macOS, Devin's sign-in subprocess runs through `/usr/bin/sandbox-exec` with a policy denying `/usr/bin/open`: the native CLI still tries that opener even in manual-token mode with remote-session markers. Failure to start the restricted command fails the attempt rather than launching an unrestricted fallback. UI accepts the current `windsurf.com/devin/account/login` link as well as `app.devin.ai/auth/cli/continue`; after visiting the copied link, paste the code the site returns into UI. See [ADR 0050](adr/0050-api-driven-worker-sign-in.md).

The `worker` Package API's `worker_runtime_list` reports each owned account backend. Codex/Grok/Devin use ACP processes; Claude uses the pinned Claude Agent SDK and does not claim one shared account PID. `worker_catalog({accountId})` reports account-bound native model IDs and dependent effort choices, a source/version, observation time, and stale/error state. `refresh: true` bypasses the thirty-minute cache, with concurrent refreshes coalesced. Devin's native model IDs are reported separately because the ACP selector may use different IDs. Catalog discovery creates no inference turn; Claude choices come from the SDK rather than a hard-coded model list. After building the packages, `STACK_NATIVE_V2_PROBE=1 node --test packages/worker/dist/test/native-v2-probe.test.js` tests OpenCode V2's isolated account catalog without spending an inference turn. `STACK_NATIVE_ACCOUNT_TURN=1 node --test packages/worker/dist/test/native-account-turn.test.js` verifies bounded Grok and Devin turns in disposable Worker worktrees when the native credentials have sufficient lifetime.

`worker_start` takes a ready account ID, an exact model ID and offered effort from `worker_catalog`, an absolute Git repository root, an optional base ref, task text and a client-generated UUID `requestId`. The base ref defaults to the source checkout's `HEAD`; uncommitted source changes are never copied. Stack creates a private branch and `<state>/workers/worktrees/<worker-id>`, returning the base commit and whether the source checkout was dirty. The new worktree receives the Role's enabled skills in `.devin/skills/` and `.opencode/skills/`; Devin's rendered instructions are a user-triggered `/prime` skill under `.devin/skills/prime/` and must be invoked manually. Self-ignored files do not enter Git status or alter a shared checkout's exclude file. Role MCP definitions and the server's local Package API MCP URLs are supplied with ACP `session/new`. OpenCode receives Role fragments in its first task message rather than as a developer instruction, a current harness limitation. The per-worker Role snapshot is private and fixed at creation; editing the Role does not change a running Worker.

`worker_start` acknowledges session setup and dispatch, not completed inference. `worker_list`/`worker_status` reveal durable phase, most recent turn and pending permission requests; `worker_read` pages bounded transcript entries by `afterSeq`. `worker_send` starts a new turn on an idle session with a fresh `requestId`, optionally changing model/effort after checking the account catalog. Repeating the identical `requestId` returns the existing Worker or turn; a different intent conflicts. `worker_respond` uses one exact pending permission ID and an offered option ID, or null to cancel. `worker_cancel` requests cancellation and requires a later status read for its outcome. `worker_close` retains the worktree and history for Bot review; `worker_remove` requires an explicit `discardWorktree: true` and keeps the Git branch. Bot-bound MCP calls require a live, sanctioned Bot thread and can operate only their Bot's Workers; local socket callers are operators.

Rich conversation reads use `worker_detail`, `worker_turn_list`, `worker_record_list/read`, and `worker_tool_list`; `worker_diff` reads the retained worktree's commits, files and patch against its base commit without writing to it. They preserve admitted prompts, observed configuration, structured tool/content records and available task-session evidence. UI clients follow Worker-scoped `worker_progress` plus `worker_changed`; progress does not start Bot wakeup turns. See [Agent trees and conversation observations](agent-trees.md) for exact cursor, retention, replay, and child-visibility contracts, and the corresponding Bot `chat_tree` reads.

For Claude collaboration, add each account through Fleet's Worker accounts menu and complete its own sign-in. Then use the same sequence as other Workers:

1. Read `worker_account_list` and select the exact ready, enabled Claude account ID.
2. Read `worker_catalog({accountId})` and choose an offered model and, when offered, an explicit effort.
3. Call `worker_start({accountId, model, effort?, repo, task, requestId})` with a fresh client UUID. Retain the returned Worker and turn IDs.
4. Read or subscribe to `worker_status`; use `worker_read` and the structured reads to inspect its output and any requested permissions.
5. Once idle, call `worker_send({id, message, requestId})` with a new UUID to ask that same Claude session for corrections or further work. Closing it retains its branch and worktree for review.

The API creates Stack-owned Claude sessions. It does not attach to an unrelated terminal session or copy an existing Claude account. See [ADR 0060](adr/0060-claude-sdk-workers.md) for the shared lifecycle and isolation decision.

`<state>/workers.sqlite` survives server restart. Interrupted turns are `unknown` and their Workers `needs_recovery`; no prompt is reissued automatically. After inspecting the worktree, `worker_resume` loads the saved native session, with `acknowledgeUnknownTurn: true` required when the last turn's outcome is unknown. If the harness cannot load that session, the record stays available for inspection. Worker records expose `sessionId` for the native session, replacing the earlier `acpSessionId` field; saved ACP session identities are preserved. `workers_changed` is a global payload-free invalidation. For completion and permission attention on the originating Bot thread, subscribe through that Bot's MCP `events_subscribe` to `{ "topic": "worker_changed", "scope": "<worker-id>", "readOperation": "worker_status", "readArguments": { "id": "<worker-id>" } }`. The server verifies Worker/Bot/thread ownership at subscription and each read, then delivers the latest changed status when that sanctioned thread becomes idle. Read `worker_read` for the bounded transcript and review the worktree before sending a fix. A subscription is not an ordered event log.

Internal MCP URLs supplied to each Worker through its native backend carry that Worker ID and current account runtime instance with an HMAC proof. The server checks the durable Worker and live runtime; positive `mcp.workerOperations` selections intersected with MCP exposure determine visible reads. Omission denies all, and read-only hints alone grant no access. Current selection is checked before calls and before releasing results. Worker records are self-only; shared Role/Brain/Content reads are explicitly selected. Closing a Worker, disabling its account or replacing its backend fences prior URLs. Role-defined additional MCP servers and same-user OS tools remain outside this Package API policy. See [ADR 0114](adr/0114-explicit-worker-disclosure.md).

The Grok and Codex ACP processes launch the verified OpenCode 2 command at `~/.local/bin/opencode` (or an explicit `STACK_OPENCODE_BIN` test override). `worker_account_login_start` runs the same sign-in for the selected account under the service — the fixed V2 binary's `auth login --standalone xai` or `auth login --standalone openai` under isolated HOME, XDG data/config/cache and provider policy, or Devin's `auth login --force-manual-token-flow` under a pty in the account's private probe directory (Devin's isolation is XDG data/config/cache only) — and surfaces only the link and one-time code, confirming the Worker when the CLI exits. `worker_account_prepare` returns that same command as a terminal fallback: run it manually, then call `worker_account_confirm({id})`; confirmation reads only that private V2 `opencode.db` credential and rejects other providers. The normal OpenCode TUI's accounts do not make a Worker binding ready and no refresh token is copied from it. The Devin ACP process launches the official native binary under `~/.local/share/devin/cli/_versions/current/bin/devin` (or an explicit `STACK_DEVIN_BIN` test override), bypassing AgentStart's terminal wrapper and its extra worktree. The terminal wrapper's `devin acp` utility pass-through is a separate operator convenience, not the server lifecycle contract.

A fresh bot starts with `mainThreadId: null`. Connect a UI to its `url` (for example, `codex --remote unix://…`) and send a first durable turn. The first persistent root thread with a materialized turn becomes the main thread. Later launches resume that ID and do not substitute another thread after a failed resume. Additional top-level Codex threads are outside Stack's bot view. Bot-scoped `threads_changed` notices invalidate state; they do not prove that the sanctioned lineage changed. An optional event scope allows a client to observe one Bot; unscoped subscriptions receive global `voice_changed` and bot notices.

The `bots` Package API also owns one ephemeral voice call across all bots. `voice_dial` takes a `botId`, client-generated `sessionId`, and gathered WebRTC SDP offer; it requires a verified running bot with an account and main thread. `voice_status`, `voice_hangup`, and `voice_changed` report and control the call without creating a new thread or transporting media through Stack. The canvas uses these operations for its call control.

On each launch, the bot snapshots the single role and currently configured server MCP URLs into a private directory passed via codexnk's required `--capabilities` flag, with `SYSTEM_APPEND.md`, `config.toml`, and enabled role-owned skills under `skills/`. Additional enabled HTTP and stdio role MCP servers join the internal connections only in that private `config.toml`. `roleRevision` is the last launched revision; edits affect the next launch. The role's `roles.sqlite` database imports the previous `capabilities.sqlite` when first opened; legacy per-launch paths remain recognized for cleanup. The private identity directory is created even for an unbound bot, so the launch never falls back to ambient Codex credentials. The executable is always `~/.local/libexec/codexnk/codex`.

The Role can also hold explicit trusted project roots. A Bot launched within an enabled root receives only that matching `[projects]` trust entry in its private `config.toml`; unrelated and disabled roots are omitted. The pinned codexnk release uses it to load project `.codex/config.toml`, including project MCP servers, while excluding home-installed skills and personal marketplaces. Already running Bots retain their prior launch behavior; loading the new runtime requires a separately authorized Bot stop/start or server restart.

Each internal MCP URL in a bot's private launch config carries a bot ID, a launch-instance digest, and a proof signed with `<state>/mcp-bot-identity.key` (mode `0600`). The server validates that proof and checks the current `bot_list` state before forwarding a tool call. A stopped or restarted bot's old URL cannot call tools. Codex tool calls include `threadId` (and sometimes `sessionId`) in MCP `_meta`; a bot-bound tool call without a thread ID is refused. The server passes `{ transport: "mcp", botId, instance, threadId, sessionId }` to the Package API operation as an optional third argument, separate from its public input schema. This is correlation metadata, not proof that the thread belongs to the Bot's sanctioned root; a turn-targeting workflow must verify lineage. The server's published MCP URLs remain ordinary local-user endpoints for humans and other local clients.

### Agent-facing event subscriptions

MCP and WebSocket manifests require explicit `operations` and `events` selections, independently: `all`, a positive name list, or `[]`. An omitted transport is disabled. Unknown and duplicate names fail validation. Socket retains every Package API operation and topic; HTTP exposes only its declared routes. Discovery reports each transport's effective `operations` and `events`. MCP admits current selection per request; WebSocket retains its handshake selection until reconnect. Gateway admission requires live socket metadata for the selected package (all configured WebSocket packages at handshake).

The server-managed MCP transport adds four tools when its event selection is nonempty: `events_catalog`, `events_subscribe`, `events_status`, and `events_unsubscribe`. `events_catalog` lists selected topic descriptions, the optional or required scope, and exposed read-only operations with their input schemas. An agent calls `events_subscribe` from its bot-bound MCP connection with `{ "topic": "…", "readOperation": "…", "readArguments": {}, "scope": "…" }`. The topic and read operation must both be selected for MCP, and the operation must advertise `readOnlyHint`. When a Bots event requires a scope, omission defaults to the caller's Bot ID; the current optional-scope API requires an explicit ID to filter to one Bot. The tool subscribes first, then returns a current value and a durable subscription ID. Repeating the same request on that thread returns its existing subscription. A Bot cannot subscribe its own thread to `threads_changed` or `chats_changed`, including through an unscoped subscription, because delivery itself would create another thread notice. UI socket and WebSocket subscriptions do not start turns and can follow their selected topics normally.

Durable watches reauthorize current exposure before and after each read and before delivery, including after queue/idle waits. Removing their operation or topic, disabling MCP, deleting the manifest, or making configuration invalid prevents subsequent reads and turns. In-flight values are discarded if authorization fails after the read. Intent and error remain recorded; a later notice or reconnect can recover after policy is restored. Already started turns are not recalled. Browse and Scrape retain `events: []` on MCP under the exposure-preserving migration; enabling their future Bot watches requires an explicit topic selection.

Subsequent notices cause a fresh read and, if its value changed, a `turn/start` containing the package, topic, scope, read operation, and current value on the subscribing thread. Bursts coalesce to the latest state. Values over 16,000 characters yield a bounded turn pointing to the read operation for the full value. The server serializes deliveries for a thread, waits for it to become idle, and checks the Bot launch and main-thread lineage again before starting the turn. It waits for that turn to complete before delivering another. A failed or ambiguous turn attempt is recorded in `events_status`; it is never blind-retried. Subscriptions live in private `<state>/event-subscriptions.sqlite` and reconnect after socket or server restart, taking a fresh snapshot and rebinding to the current verified Bot launch. `events_unsubscribe` removes one exact ID for the same Bot thread. An unloaded thread remains in error/retry state until it returns or is unsubscribed; a deleted Bot's subscriptions are pruned on rebind. No other thread is substituted. Notices are invalidations, not a replayable event history.

On startup, the Bots Package API verifies recorded process ownership, reaps children from a previous server, and relaunches recorded bots, including stopped ones. An unverified PID/endpoint pair remains fenced with `recoveryIssue`; it is not killed merely because the record says running. A verified stop clears the issue. An existing Package API socket is never unlinked to claim a second instance. If `<state>/sockets/bots.sock` is left by a crash, inspect its listener and server before removing only that verified stale path. App-server sockets are cleaned only after their known child stops.

The server refuses a second `serve` against a running instance and checks fixed ports before claiming sockets. On shutdown it closes public ingress and drains active calls while dependencies remain. The `signal` child stops before `infer`, and `worker` stops before `bots`; `browse` drains Browser profiles during its planned shutdown before its process group is signalled. The Worker child stops its account backends and the Bots child stops its app-server processes. Brain cancels execution and observer waits before draining its socket calls, then stops its Share ingress and releases its resources; see [Brain and device sharing](brain.md). The server does not restart failed children automatically. The `/` open bench and its global API reference reflect the live Package API catalog. `serve_status` reports the UI entry and canvas URLs; the Server window links to `/?reference=overview`. The standalone docs listener, its HTML/Markdown URLs, `stack docs`, `STACK_DOCS_PORT` and `serve_status.docsUrl` are retired; consumers should use UI or the existing discovery operations.
