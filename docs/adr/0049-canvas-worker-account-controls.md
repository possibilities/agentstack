# 49. Operate Worker accounts from the canvas

Status: accepted, 2026-09-25. Extends [ADR 0026](0026-canvas-auth-controls.md) and fulfils the "separate UI request" noted in [ADR 0048](0048-separate-bot-and-worker-sign-ins.md).

Extended by [ADR 0060](0060-claude-sdk-workers.md) with Claude account creation, native sign-in and usage/catalog parity in these same Fleet surfaces.

The Fleet space now reads Worker accounts | Bot accounts | Bots in three columns. The Bot accounts window keeps its `accounts` id and device sign-in; a new `worker-accounts` window groups Worker accounts under CODEX / GROK / DEVIN sections. Each account window creates only its own kind — the Bot accounts window starts the Codex Bot device sign-in, and the Worker accounts window's menu offers the Codex, Grok, and Devin Worker sign-ins; account windows never cross-create. The command palette, which is not a window, offers all four.

Worker sign-in is API-run ([ADR 0050](0050-api-driven-worker-sign-in.md)), not a terminal command. `worker_account_login_start` returns an attempt the card tracks as a sign-in panel. All providers share the same order and inset rows: short instructions, a copyable link (never opened — the canvas has no `window.open` or auth `target="_blank"` anywhere), a code area, status with an elapsed timer, and Cancel. Codex/Grok show a copyable one-time code; Devin shows a labelled paste-back input and "Submit code" while `needsCode` is set. The status distinguishes waiting for approval, waiting for a code, submitting, and waiting for sign-in. A new attempt resets the draft and timer, while a failed submission preserves the draft for retry. Finished attempts show "Signed in" or the error with "Try again" until dismissed. Re-signing in a *ready* Worker drains its ACP process, so the card asks for confirmation first ("Sign in again to grok-1?"). Enable/disable, "Sign in again", finish-removal, and remove are per-card controls; the Worker remove dialog states that the ACP process stops and private credentials are deleted while Bot accounts are unaffected. Worker pending and error state lives in a separate `worker` action object so it can never be confused with Bot account state.

Worker cards use a distinct `worker-account` node kind because legacy Worker IDs may equal a Bot account UUID — keys, selection, and links never collide. `linkedAccounts` is drawn as a dotted neutral connector between the two cards and as chips on each card that navigate to the counterpart; per ADR 0048 it is descriptive only. The Bot remove dialog notes that linked Worker accounts stay signed in.
