# 49. Operate Worker accounts from the canvas

Status: accepted, 2026-09-25. Extends [ADR 0026](0026-canvas-auth-controls.md) and fulfils the "separate UI request" noted in [ADR 0048](0048-separate-bot-and-worker-sign-ins.md).

The Fleet space now reads Worker accounts | Bot accounts | Bots in three columns. The Bot accounts window keeps its `accounts` id and device sign-in; a new `worker-accounts` window groups Worker accounts under CODEX / GROK / DEVIN sections. Each account window creates only its own kind — the Bot accounts window starts the Codex Bot device sign-in, and the Worker accounts window's menu offers the Codex, Grok, and Devin Worker terminal sign-ins; account windows never cross-create. The command palette, which is not a window, offers all four.

Worker sign-in is a terminal flow, not a device code. `worker_account_prepare` returns a shell command the canvas holds in memory only and shows in a mono block on the card ("Run this in a terminal, then confirm."); `worker_account_confirm` marks the account ready and drops the held command. Re-preparing a *ready* Worker drains its ACP process, so the card asks for confirmation first ("Sign in again to grok-1?"); an unready Worker re-prepares directly, which is also how a lost command is shown again. Enable/disable, "Sign in again", finish-removal, and remove are per-card controls; the Worker remove dialog states that the ACP process stops and private credentials are deleted while Bot accounts are unaffected. Worker pending and error state lives in a separate `worker` action object so it can never be confused with Bot account state.

Worker cards use a distinct `worker-account` node kind because legacy Worker IDs may equal a Bot account UUID — keys, selection, and links never collide. `linkedAccounts` is drawn as a dotted neutral connector between the two cards and as chips on each card that navigate to the counterpart; per ADR 0048 it is descriptive only. The Bot remove dialog notes that linked Worker accounts stay signed in.
