# Proc: local schedules and processes

Proc is an owner-supervised Package API. Its full operations and events are available over the local socket, Bot MCP, and loopback WebSocket. Worker-bound MCP connections still follow the shared read-only Worker policy. Proc runs as the owner user, **not** in a sandbox; schedules and process launches are intentional execution authority, even when admitted by an agent. It has no HTTP device route or dedicated UI controls. Its SQLite ledger lives in `<AGENTSTACK_STATE_DIR>/proc/proc.sqlite`. No legacy process or scheduler state is imported.

## Schedules

`proc_schedule_create` takes an optional caller-selected UUID `id`, an `action`, `firstAt` (ISO timestamp with offset), `everyMs` (null for one shot, otherwise 1 second through 31 days), and `enabled`. A repeated create with the same ID and identical definition returns the existing schedule; a different definition at the same ID is refused. `proc_schedule_update` and `proc_schedule_remove` require `expectedRevision`. Removal prevents future admissions but preserves execution history and does not cancel a running invocation. An update resets the next due time to its new `firstAt` and does not change an already admitted invocation.

An API action is `{ "type":"api", "package":"brain", "operation":"sources_sync", "input":{"due":true} }`. Proc checks that the operation is on the **live socket** when registered and before dispatch; the target validates input itself. A process action is `{ "type":"process", "process": { "command":"/absolute/executable", "args":[], "timeoutMs":300000, "retainOutput":true } }`; optional `cwd` must be absolute, and optional `env` overrides are stored privately with the schedule. No shell parsing or PATH resolution occurs.

The protected system schedule calls Brain `sources_sync` with `due:true` every five minutes. Brain's own persisted Source cadence still decides what is due, and fresh installations have no enabled Sources. It queues discovery through the Brain Ingestion worker; it does not wait for discovered child URLs to finish indexing. The system schedule cannot be edited or removed through Proc.

`proc_schedule_list/get` report the next due time; `proc_execution_list/get` report each admitted invocation and a bounded result. After sleep, at most one overdue interval is admitted per schedule. While an invocation is running, that schedule does not overlap itself. A response lost across an API call is reported as **unknown**, not retried: the target may have performed its effects. Future intervals remain eligible. Targets needing exactly-once effects must supply and enforce their own idempotency key in the scheduled input. A known pre-dispatch target failure is `failed`, distinct from an ambiguous call.

## Processes

`proc_run_start` requires a caller-generated UUID `requestId` for retry-safe admission. It returns a run record immediately. Resending the same ID and process specification returns the same run; changing the specification is refused. `proc_run_get/list` report its state, PID while running, exit code/signal when known, output count, and truncation flag. `proc_run_cancel` requests process-group termination and returns the current record; read again to establish the outcome.

Each process has an IPC guardian. If Proc loses its owner connection, the guardian terminates its process group. Proc restart records interrupted runs as **unknown** rather than guessing an exit code. The default process timeout is five minutes; use `timeoutMs:null` for a deliberately long-running follower and cancel it explicitly. Output is framed as ordered stdout/stderr lines, with long lines split into marked partial chunks. At most 2 MB / 10,000 chunks are retained per run; `outputTruncated` reports the bound. `retainOutput:false` discards recorded lines at exit; fast producers may outpace a live follower, so use retention when every line matters. Terminal history is pruned after 30 days.

`proc_run_read` pages output after a monotonically increasing `after` cursor. `proc_run_wait` waits at most 30 seconds for another line or exit and returns the same page; `proc_run_join` waits for exit alone, up to five minutes, and reports observer timeout without cancelling the run. Direct socket callers must give `socketCall` a timeout longer than `waitMs` (its default is ten seconds); MCP and WebSocket forwarding allow these operations' declared bounds. These reads do not repeat execution.

Topics `proc_output_changed`, `proc_runs_changed`, and `proc_schedules_changed` are payload-free on the event-capable transports. Each captured line publishes an output notice, optionally scoped to its run ID. **Do not count notices to reconstruct output**: they may be coalesced or lost on disconnect. Resnapshot with `proc_run_read` using the last cursor. Schedule and run topics may likewise be scoped by their stable IDs. No notification is a human approval or a system banner.

See [ADR 0105](adr/0105-proc-local-scheduling-and-process-control.md) for the ownership and failure boundaries. Civil-time alarms, reminders, time zones and user-facing controls are reserved for later Clock design.
