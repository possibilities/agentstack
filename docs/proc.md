# Proc: local schedules and processes

Proc is a server-supervised Package API. Its full operations and events are available over the local socket, Bot MCP, and loopback WebSocket, with operation-level ownership checks. Worker-bound calls have no Proc ownership contract and are refused. Proc runs as the server user, **not** in a sandbox; schedules and process launches are intentional execution authority, even when admitted by an agent. It has no HTTP device route or dedicated UI controls. Its SQLite ledger lives in `<AGENTSTACK_STATE_DIR>/proc/proc.sqlite`. Only Proc's own older schema is migrated; no external process or scheduler state is imported.

## Schedules

`proc_schedule_create` takes an optional caller-selected UUID `id`, an `action`, `firstAt` (ISO timestamp with offset), `everyMs` (null for one shot, otherwise 1 second through 31 days), and `enabled`. A repeated create with the same ID, authority and identical definition returns the existing schedule; a different definition or authority is refused. `proc_schedule_update` and `proc_schedule_remove` require `expectedRevision`. Removal prevents future admissions but preserves an ownership tombstone and execution history; it does not cancel a running invocation. Removed IDs cannot be reused. An update resets the next due time to its new `firstAt` and does not change an already admitted invocation.

Proc assigns `createdBy`, `lastEditedBy` and `authority`. Bot authority captures its ID, durable `mainThreadId` and sanctioned calling `threadId`, not its replaceable launch instance. Bots read and manage only their own root's schedules, executions and runs. Operators manage non-system schedules, but operator edits never promote Bot authority. Create a new operator-owned schedule when that is intended. Worker-bound identities are never treated as operators.

An API action is `{ "type":"api", "package":"brain", "operation":"sources_sync", "input":{"due":true} }`. Operator targets must exist on the live socket. Bot targets must also be selected by current MCP exposure at registration and dispatch. Proc revalidates the current Bot/root/thread and forwards explicit scheduled invocation context, so downstream operator-only and ownership guards continue to apply. Proc cannot target itself. The target validates input itself. A process action is `{ "type":"process", "process": { "command":"/absolute/executable", "args":[], "timeoutMs":300000, "retainOutput":true } }`; optional `cwd` must be absolute, and optional `env` overrides are stored privately with the schedule. No shell parsing or PATH resolution occurs.

The protected system schedule calls Brain `sources_sync` with `due:true` every five minutes. Brain's own persisted Source cadence still decides what is due, and fresh installations have no enabled Sources. It queues discovery through the Brain Ingestion worker; it does not wait for discovered child URLs to finish indexing. The system schedule cannot be edited or removed through Proc.

`proc_schedule_list/get` report the next due time, attribution, authority, `blockedReason` and `retryAt`. A stopped/unavailable Bot, unavailable thread or withdrawn target exposure holds the occurrence, retrying at most once per 30 seconds. A valid restart resumes it. Missing Bots and changed roots block without automatic retry. Pre-admission refusal consumes no one-shot and produces no execution. `proc_execution_list/get` report captured action/authority and a bounded result. After sleep, at most one overdue interval is admitted per schedule. Running invocations do not overlap themselves. A response lost across an API call or an unclassified downstream error is **unknown**, never automatically retried: effects may already have happened. A known shutdown refusal before dispatch is `refused`. Future intervals remain independent. Targets needing exactly-once effects must enforce their own idempotency key.

### Existing schedules

Schema v1 schedules retain their definitions and history but become disabled with null authority, `createdBy: { "kind":"legacy_unknown" }`, and `blockedReason: "legacy_reauthorization_required"`. Operators explicitly review and submit the full definition to `proc_schedule_reauthorize`, with `id` and `expectedRevision`, to assign operator authority and choose whether to enable it. Ordinary edits cannot bypass this step or promote Bot schedules. Only the exact protected Brain due-source schedule retains automatic authority. Historical execution attribution is not invented.

## Processes

`proc_run_start` requires a caller-generated UUID `requestId` for retry-safe admission. It returns a run record immediately. Resending the same ID, actor and process specification returns the same run; changing the specification or actor is refused. `proc_run_get/list` report attribution, state, PID while running, exit code/signal when known, output count, and truncation flag. Bots can read output or cancel only their own root's direct and scheduled runs. `proc_run_cancel` requests process-group termination and returns the current record; read again to establish the outcome.

Each process has an IPC guardian. If Proc loses its server connection, the guardian terminates its process group. Proc restart records interrupted runs as **unknown** rather than guessing an exit code. The default process timeout is five minutes; use `timeoutMs:null` for a deliberately long-running follower and cancel it explicitly. Output is framed as ordered stdout/stderr lines, with long lines split into marked partial chunks. At most 2 MB / 10,000 chunks are retained per run; `outputTruncated` reports the bound. `retainOutput:false` discards recorded lines at exit; fast producers may outpace a live follower, so use retention when every line matters. Terminal history is pruned after 30 days.

`proc_run_read` pages output after a monotonically increasing `after` cursor. `proc_run_wait` waits at most 30 seconds for another line or exit and returns the same page; `proc_run_join` waits for exit alone, up to five minutes, and reports observer timeout without cancelling the run. Direct socket callers must give `socketCall` a timeout longer than `waitMs` (its default is ten seconds); MCP and WebSocket forwarding allow these operations' declared bounds. These reads do not repeat execution.

Topics `proc_output_changed`, `proc_runs_changed`, and `proc_schedules_changed` are payload-free on the event-capable transports. Each captured line publishes an output notice, optionally scoped to its run ID. **Do not count notices to reconstruct output**: they may be coalesced or lost on disconnect. Resnapshot with `proc_run_read` using the last cursor. Schedule and run topics may likewise be scoped by their stable IDs. No notification is a human approval or a system banner.

See [ADR 0105](adr/0105-proc-local-scheduling-and-process-control.md) and [ADR 0110](adr/0110-proc-durable-caller-authority.md) for the lifecycle and authority boundaries. The live API reference exposes these schemas, but dedicated schedule/run and reauthorization controls still need a separate UI decision. Civil-time alarms, reminders and time zones are reserved for later Clock design.
