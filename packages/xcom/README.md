# Xcom following archive

Xcom is an API-only AgentStack package for best-effort research over the X following feed. It uses the authenticated local `twitter` CLI (`twitter-cli` as used by `../xarchive`); set `AGENTSTACK_XCOM_TWITTER` to its executable if it is not on `PATH`. It does **not** use Brain's ingestion ledger, Scrape's browser, or semantic embeddings. Retrieval is FTS5, like Brain.

The default state is `<AGENTSTACK_STATE_DIR>/xcom/following.sqlite3` (normally `~/.local/state/agentstack/xcom/following.sqlite3`). The service creates a **new empty** private database; it does not discover, import, or modify `~/.local/share/xarchive/following.sqlite3`. **Scheduled collection is off by default** so it does not compete with the still-running xarchive seeding. After the deliberate migration, set `AGENTSTACK_XCOM_AUTO_SYNC=1` for the owner and restart it with authorization. Then startup triggers a background head pass, and an hourly wake checks for a due head pass (six-hour cadence), unfinished backfill (initial two calendar months), then missing full X Articles. `xcom_status.auto_sync` reports this setting. `xcom_sync` and `xcom_articles_sync` work even when scheduling is off; they trigger asynchronous work. Use `xcom_status` to check saved cursor, progress, stop reason and errors. A feed request is paced 20–40 seconds from the previous CLI request. Transient CLI failures retry the same cursor with 1/2/4-minute backoff. Other failures pause until the next sync; a missing or unauthenticated CLI is reported as an error, not treated as an empty feed. The CLI may rate-limit or omit/truncate posts; neither the cutoff nor an end-of-feed response proves complete historical coverage.

`xcom_search` accepts `scope: "tweets" | "articles" | "all"`, FTS5 `mode: "any" | "all" | "raw"`, `sort: "relevance" | "recent"`, `author` or stable `authorId`, `dateFrom`/`dateTo` (post creation dates), `archivedFrom`/`archivedTo` (first archived dates), `hasArticle` or `articleState: "fetched" | "unfetched" | "none"`, `limit` and `offset`. A post with both matching text and article is two hits with the same `tweet_id` and distinct `kind`. `xcom_context` adds citation-ready full text under a total character budget. `xcom_list` traverses posts without a query; `xcom_get` reads the immutable feed JSON and any fetched full article. `xcom_articles_pending` pages posts whose article body is still missing and `xcom_status` reports the pending/unavailable counts. `xcom_users` and `xcom_user_get` show authors *observed* in cached feed pages; they are **not** the accounts-followed graph. Filter by stable author ID if a handle has changed or been reused. Full article bodies are indexed only after a successful `twitter article ID --json` call; failed/inaccessible articles remain eligible for later catch-up (unavailable ones are retried after one day).

## Later database migration (not performed by setup)

Finish the separate xarchive seeding first. Stop **both** the xarchive writer and the Xcom owner child before taking a SQLite-consistent backup of xarchive's database; do not copy a live database file without its WAL. Keep an independent backup of the source. Only after reviewing the destination and deliberately replacing its *empty* Xcom database should the operator place the snapshot at the Xcom path with private permissions. Do not overwrite a nonempty Xcom database. Restart Xcom; its startup transaction upgrades the FTS indexes, preserves saved scan cursors and populates observed authors. `xcom_reindex` repairs the derived indexes later. Xcom never needs access to the original xarchive directory, and migration does not merge two archives or change the CLI account identity. Confirm the CLI is authenticated to the same account before resuming collection.

No UI has been requested. A future UI could show head/backfill health, article catch-up, and search filters in a dedicated research view; currently use the Package API or its MCP exposure.
